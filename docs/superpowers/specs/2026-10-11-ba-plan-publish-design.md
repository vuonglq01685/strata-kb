# BA plan on the hub — publish missions & tickets, and keep them current

Status: approved direction, builder-checked · 2026-10-11

## 1. Intent

Today a `ba` repo never publishes (README §12, `config-ba.yaml`: "a ba repo
never publishes"). Mission plans and Dev-ready tickets live only in the BA
repo and in the tracker paste from `kb ticket export`. Dev agents, SAs and
other teams searching the hub see *what exists* (`-code`, `-svc`, ingested
documents), never *what is planned*.

The project owner wants the plan on the hub now. Who may read it is decided
later and is out of scope.

Second problem: a mission is written once, up front, and reality then moves.
Cited KB content changes, the architecture changes, scope changes, and
delivery teaches something new. Today only KB-citation drift is detected
(`kb-doctor.yml` runs `kb ticket stale`, which keeps one `kb-stale-citations`
issue), and there is no supported way to *amend* a mission:
`ba-mission-plan` only writes new ones.

This design covers both:

- **A. Publish:** the BA publishes, on demand, every reviewed mission and
  every DoR-passed ticket as one generated hub document, `<repo_id>-plan`.
  The trigger is `kb publish` / `/kb-publish`, the same tag-driven intake flow
  child repos use.
- **B. Keep current:** detect architecture drift as well as KB drift, give
  the BA an amend mode, record every change, and propagate it to the stories
  without rewriting history.

## 2. Goals, non-goals, anti-goals

Goals

1. `kb publish` in a `ba` repo publishes `<repo_id>-plan` through the existing
   tag → `kb-publish.yml` → `kb ci-publish` → intake → hub-PR path. The hub
   needs no code change.
2. Only reviewed material is published: missions that pass `kb mission lint`
   **and** have a fully ticked `## Definition of Ready`, and tickets that pass
   `kb ticket lint` and have a fully ticked `## Definition of Ready`.
3. The daily `kb-doctor` sweep also reports architecture drift: a section a
   mission or ticket was grounded on has changed, or disappeared, on the hub
   since its `Grounded on:` revision.
4. The BA can amend a mission or a ticket with a guided flow. Every amendment
   bumps a revision and appends a change-log row.
5. Delivered stories are never rewritten. Change lands as new stories or as
   superseding decisions.

Non-goals

- Access control on the hub (who may read `-plan`).
- Automatic publish on merge. Hub intake accepts only `refs/tags/kb-publish/*`
  tokens (`intake.py:367`). Changing that is a hub security change the owner
  declined.
- Changing the tracker flow. `kb ticket export` pasted into Jira stays as is;
  the hub copy is a reference copy.
- Publishing drafts or `## Review record` / `## Definition of Ready` content.
- Tickets citing their mission through `## KB context`.
- Machine-enforcing the B4 change rules against git history. They are enforced
  by the amend skills, plus the two tool changes named in B4.
- Fixing `kb-code.yml`'s own publish-on-push job. It hits the same intake
  rule; this is noted for the owner and is out of scope.
- Any hub web-UI change.

Anti-goals (a failure even if it "works")

- CI writing, editing or committing anything in the BA repo.
- Drift noise: flagging missions whenever the dev repo merges a commit.
  `-code`'s revision moves on every dev commit, so drift is judged per cited
  section, never on the whole-document revision.
- Breaking existing `ba` repos. A mission or ticket written before this change
  must still lint PASS.
- Renumbering or reusing a story id (`M-x-US<n>`). Those ids are cited in
  trackers, PRs and `-svc` history.

## 3. Constraints (verified in the codebase)

**Publish path (B flow)**
- `kb publish` → `publish.plan()` (`publish.py:1200`). For any non-hub kind
  with `intake:` set, it takes route `intake`.
- `publish_via_intake` (`publish.py:~1600`):
  - refuses a dirty `.kb/`;
  - tags `kb-publish/<ts>`, pushes the tag, and polls `/intake/status`.
- `kb-publish.yml` runs `kb ci-publish` on that tag with OIDC.
- Intake `authorize` (`intake.py:362`):
  - accepts only `refs/tags/kb-publish/*`;
  - needs a registry entry for the repo (`federation/registry.yaml`). That
    entry, never the payload, decides the write path;
  - an entry pinned with `workflow:` rejects every other workflow file.
- `plan()` already has the hook this design mirrors. It sets
  `refresh_code = kind == "dev"`, and the CLI then refreshes `-code` before
  publishing (`cli.py:2004`, `_refresh_dev_code`).

**Generated documents**
- `kb code-ingest` (`codeingest/core.py`) is the pattern to follow. It writes
  `<group>.md` (L2) and `<group>.raw.md` (L3) per group, plus
  `_manifest.yaml`. It upserts `.kb/index.yaml`, prunes group files it no
  longer produces, and banners each file
  `> Generated by … — do not edit by hand.`
- `build._check_tables` (`build.py:170-205`) requires L2's tables to equal
  L3's tables: the **same set, in the same order**. An L3 table missing from
  L2 fails `kb build`.
- Section headings are `## <sid> <title>` (`mdutils.HEADING_RE`, where sid is
  `\S+`). Inner `##` headings of a mission or ticket would parse as sections,
  so they must be demoted.

**Drift detection**
- `resolve.py` compares a section at a pinned **hub commit** with the hub
  worktree (`gitio.rev_exists`, `read_at`) and yields `ok | stale | broken`.
  `kb ticket stale` uses it for `## KB context` refs.
- `Grounded on: <repo>:<repo>-code @ <revision>` is the `-code` manifest
  revision, i.e. the **dev repo's** short commit, not a hub commit
  (`ticketcheck.py:36-52`, `codeingest/core.py:366-399`). A
  comma-separated list may name `-code` and `-svc`; the `-code` entry wins
  (`missionnext.grounded_doc`).
- `kb ticket check` fails when `Grounded on` differs from `-code`'s current
  revision (`ticketcheck.py:496-503`).

**Lint and status**
- `## Review record` lint (`lintcore.py:479-610`) has four rules: rounds
  strictly increasing, rounds 2–3 by `gap-verifier`, more than 3 rows is a
  warning, and maturity read from the last row.
- `kb mission lint` treats a missing Review record as a warning and does not
  check the DoR ticks. It does not validate decision statuses
  (`missionlint.py:222-262`).
- `kb ticket check` errors on any `[NEW: D<k>]` whose row is not `DECIDED`
  (`ticketcheck.py:363`).
- `kb mission next` treats a non-`DECIDED` row in `Blocks` as blocking
  (`missionnext.py:231`).

**Init**
- `kb init --kind ba` writes the `BA_TEMPLATES` map (`initcmd.py`).
  `.kb/config.yaml` and `.claude/settings.json` are `PROTECTED_FILES`, never
  rewritten without `--force`. `BA_LOCAL_OVERRIDES` are created once.
  `BA_TEMPLATES` today has no `kb-publish` skill or workflow and no
  `.gitattributes`. Dev and child repos get `.kb/** -text`, which publish
  hashing relies on.
- `kb ci-publish` also reads the intake URL from `STRATA_KB_INTAKE`.
- Agent workflows ship in four flavours per skill: Claude skill, Claude
  command, Copilot prompt, Cursor command. `kb-publish` has no Claude command
  (`initcmd.py:254`).

## 4. Part A — publish `<repo_id>-plan` on demand

### A1. `kb plan-ingest`

A new command, the `ba` twin of `kb code-ingest`. It is deterministic, needs
no LLM and no hub, and runs offline.

**Input:** `missions/*.md` and `tickets/**/*.md`, with the same defaults and
`--missions-dir` / `--tickets-dir` flags as the other BA commands.

**Selection:**

| Item | Published when |
|---|---|
| Mission | structural `kb mission lint` passes **and** every `## Definition of Ready` box is ticked |
| Ticket | structural `kb ticket lint` passes **and** every `## Definition of Ready` box is ticked **and** `kb mission next` would not demote it to `draft` (B4) |

- Citation resolution is **not** a publish gate. It needs the hub, and
  `kb-ticket-lint.yml` already gates PRs on it. Call the lint functions in
  Python, not as subprocesses. If structure and citation checks are entangled,
  split them so `plan-ingest` runs offline.
- Skipped items print as `skipped: <file> — <reason>`, and also go to the
  GitHub step summary when running in Actions. A skip never fails the command.
- Exit `1` only on an unreadable or malformed input that the lints report as
  an error, or on a bad flag.

**Output:** `.kb/<repo_id>-plan/`, written exactly the way `code-ingest`
writes its doc. That covers the manifest, the index upsert, pruning, and the
banner `> Generated by kb plan-ingest at <short-commit> — do not edit by
hand.`

- **Groups:** one per mission, as `M-<slug>.md` / `M-<slug>.raw.md`. Tickets
  whose `> Parent mission:` names a *published* mission go in that mission's
  group. All other tickets go in group `tickets`.
- **Sections:**
  - mission: `## M-<slug> <mission title>`;
  - ticket: `## <stem> <ticket title>`, where the stem is `M-<slug>-US<n>`
    for mission stories, else the file stem.
- **L3 (`.raw.md`):** the source verbatim, with these changes:
  - the H1 is dropped (it becomes the section title);
  - every heading is demoted one level (`##` → `###`, and so on). Fenced
    blocks are untouched;
  - `## Review record` and `## Definition of Ready` are removed;
  - `## Open questions` is kept.
- **L2 (`.md`):** every table of the L3 section, in L3 order, byte-identical.
  Add the prose of Summary and Business goal (missions) or the story and
  acceptance criteria (tickets). Drop all other prose and every Mermaid block.
  Do **not** relax `build._check_tables`.
- **Manifest:** `title: "<repo_id> — plan"`, `revision: <short-commit>`.
- **Index entry:** tagged so `kb_search` users can filter plans. Follow how
  `-code` is tagged.
- **Review gate:** the generated sections must pass `kb ci-publish`'s
  unreviewed gate the same way `-code` does. A BA's DoR tick is the review.

**Unpublishing:** an item that stops qualifying drops out of `-plan` on the
next publish. That is intended. The `/kb-publish` skill already shows the BA
the diff against the published snapshot before confirming, so a removal is
seen before it ships. No placeholder is kept.

### A2. `kb publish` in a `ba` repo

- `publish.plan()` gains `refresh_plan = kind == "ba"`. When it is set, the
  CLI runs `kb plan-ingest` and `kb build` before the publish route, the way
  `refresh_code` refreshes `-code`. This makes the local diff preview show the
  `-plan` that CI will send.
- `.kb/<repo_id>-plan/` is gitignored in a `ba` repo, so regenerating it never
  makes `.kb/` dirty. In a `ba` repo `.kb/index.yaml` is also generated and
  gitignored (a committed copy tripped the dirty-`.kb` refusal on first
  publish; `kb ci-publish` enumerates files with rglob, so ignored files
  still upload).

### A3. `ba` scaffolding (`kb init --kind ba`)

Add to `BA_TEMPLATES`:

- `.github/workflows/kb-publish.yml`, from a new `kb-publish-ba.yml` template.
  It is the same as `kb-publish.yml` (tag trigger, `id-token: write`, pinned
  action SHAs), but runs `kb plan-ingest`, `kb build`, `kb ci-publish`.
- The `kb-publish` skill in its three flavours, reusing the existing
  templates. Check that their wording does not assume ingested PDFs. Adjust it
  through the existing local-override mechanism or a `ba` wording branch, not
  a fork.
- `.gitattributes` with `.kb/** -text`, as dev and child repos get.
- A `.gitignore` merge entry for `.kb/*-plan/`, using the existing merge-only
  `.gitignore` handling.

`config-ba.yaml` (new repos only, because the file is protected):

- `repo_id` is no longer "informational only". It names `<repo_id>-plan` and
  must match the hub registry entry.
- Add `intake: ""`, with the same comment wording as the child config.
- Rewrite the header: a `ba` repo publishes its plan, never KB content.

Existing `ba` repos: a QUICKSTART step tells the BA to add
`intake: <url>` to `.kb/config.yaml` and re-run `kb init --kind ba`.

### A4. Hub operator step (documented, no code)

Register the BA repo in `federation/registry.yaml` like any child, and
optionally pin `workflow:` to its `kb-publish.yml`. Document this in
QUICKSTART-ba and README §12.

### A6. Dev side — a ticket id is enough (owner decision, added during build)

A Dev given only a ticket id (`M-<slug>-US<n>`, or a plain ticket stem)
gets the ticket **from the hub first**.

- New `kb ticket fetch <id> [--out <path>] [--hub <url>]`:
  - finds the federation repo(s) publishing a `*-plan` document whose
    manifest has section `<id>`. `<repo>:<id>` qualifies the id when
    several repos hold it;
  - not found → exit 1 with a clear message (not published yet: ask the
    BA to `kb publish`, or pass a path or paste). Ambiguous → exit 1,
    naming the holders;
  - writes the ticket restored to its source shape:
    - `# <section title>`;
    - one provenance line,
      `> Fetched from hub: <repo>:<doc> §<id> @ <hub short rev> — do not edit; amend in the BA repo.`;
    - the L3 body with every heading promoted one level (fence-aware, the
      inverse of plan-ingest's demotion);
  - the default `--out` is `docs/impl/<id>/ticket.md`, overwritten on every
    fetch. It is derivable, so `docs/impl/.gitignore` ignores
    `*/ticket.md`.
- The dev skills' Intake order becomes:
  1. id only → `kb ticket fetch <id>`. With no CLI, use MCP `kb_get_section`
     for `<doc> §<id>` at `l3`, then save it as above;
  2. a path or a pasted body still works, as the fallback when the hub has
     no copy or is unreachable.
  The parent mission's `## Sequencing` is read from the hub the same way
  (`kb get <doc> <M-id> --level l3`) when there is no local mission file.
- The hub copy has no `## Definition of Ready` (plan-ingest drops it).
  Being on the hub means its DoR was fully ticked. No dev step may require
  that section.

### A7. Plan status on the hub, in its own UI menu (owner decision, added during build)

Ticket and mission status is **derived, read-only**, from what the hub
already holds. Nothing new is stored and there is no new write path:

- **Missions and backlog:** the `M-<slug>` sections of every `<ba-repo>-plan`.
- **Published ticket:** a `M-<slug>-US<n>` section exists in that `-plan`.
  Being published means its DoR passed.
- **Done:** the story id is in a `hist.*` row of the dev repo's `-svc`. The
  `-svc` is found from the mission's `Grounded on:` line, exactly as
  `kb mission next` does today.

Hub status per story. The order is the same as `missionnext.statuses`:

1. `done`
2. `ready` (ticket published)
3. `to-draft`, shown as **not ready**: no published ticket, dependencies done
4. `blocked`, with its reasons

The repo-only states (`draft`, and the parent-revision demotion) cannot be
seen on the hub: such tickets are not published, so they show as not ready.

**CLI:** `kb mission next --from-hub [--repo <ba-repo-id>] [--json]`
computes the same report from the hub alone. It needs no `missions/` or
`tickets/` directory and uses the configured or `--hub` hub.

**UI:** a separate left-rail menu, **Plans**, at the same level as
Documents.

- `/ui/plans` lists the BA repos and their missions, each with status
  counts; `/ui/plans?repo=<id>` shows one repo, including its "tickets
  without mission".
- `/ui/plans/{mission}?repo=<id>` shows the mission summary and the backlog
  table, with each story's status, its reasons, and a link to its ticket.
- `/ui/plans/{mission}/{story}?repo=<id>` shows the ticket (L3, rendered
  like the section reader). Unparented tickets use
  `/ui/plans/tickets/{story}?repo=<id>`.
- The repo is a query parameter, as on `/ui/docs`, because nested federation
  ids contain `/`. Without `?repo=` the unique holder is used. Several
  holders give a 404 page that names them.

`*-plan` documents no longer appear under Documents: not in the catalog,
not in the overview counts, not in the tag rail. Search still finds plan
sections, but a hit in a `-plan` document links to its Plans page.

Out of scope: an "in progress" state, assignees, and any status writes.
The tracker stays the place for those.

### A5. Docs

- `QUICKSTART-ba.md`: registry, intake, `/kb-publish`.
- The `kb init` next-steps text for `ba`.
- The PDF guides under `docs/` are regenerated by their own pipeline. That is

## 5. Part B — keep missions and tickets current

### B1. Revision and change log

The mission template and the ticket template gain:

- under the title, `> Revision: <N>` (an integer, starting at 1);
- an append-only `## Change log` placed before `## Review record`:

  | Rev | Date | Trigger | What changed | Affected | Review |
  |---|---|---|---|---|---|

  - `Trigger`: one or more of `kb-context`, `architecture`, `scope`,
    `delivery`, comma-separated.
  - `Affected`: US ids (mission) or section names (ticket), or `-`.
  - `Review`: the amendment's maturity scores, e.g. `B4 D4 (agent)`.

Amendment reviews are recorded **here, not in `## Review record`**, so its
round rules and its maturity reading stay untouched.

Lint (`kb mission lint`, `kb ticket lint`):

- `Revision` absent: treated as `1`, with a warning only. Old files stay PASS.
- `Revision: N` with `N > 1`: the change log must have exactly one row per
  revision `2..N`, in order. Otherwise FAIL.
- Unknown `Trigger` value: FAIL.

### B2. Architecture drift in `kb ticket stale`

Extend `kb ticket stale`, and through it `kb-doctor.yml`, with **no workflow
change**.

**Ref sources:**
- Missions: the `svc.*` ids in `## Services & order`.
- Tickets: the `svc.* / db.* / api.* / int.* / cmd.*` ids in
  `## Technical grounding`.
- Ids carrying `[NEW: D<n>]` are skipped.
- The baseline is the `-code` entry of `Grounded on:`, as
  `missionnext.grounded_doc` reads it.

**Baseline mapping:** find the hub commit whose
`federation/<repo>/<repo>-code/_manifest.yaml` carries `revision:` equal to
the pinned revision. Use the newest such commit, found by walking that file's
hub history with the existing `gitio` helpers. Then build refs
`<repo>-code §<id> @ <hub-commit>` and run them through the existing
`resolve.py` comparison:

- content changed: `stale`;
- section gone: `broken`;
- no hub commit carries the revision (the hub PR was never merged, or was
  superseded): one `stale` finding for the file with reason
  `baseline not on hub`.

Findings carry reason `architecture` in `--md` and `--json`, next to the
existing KB-context findings. Exit codes are unchanged (`0` / `2` / `1`).

Only cited sections are compared, so a dev merge that touches nothing a
mission used yields nothing.

### B3. Amend mode

Two new modes, each shipped in all four flavours: `ba-mission-plan --amend
<M-id>` and `ba-ticket-author --amend <ticket>`.

1. Read the file and the `kb ticket stale --md` findings for it.
2. Ask the BA for the trigger(s) and what changed. Drift findings pre-fill
   this.
3. `kb-context` trigger: re-pin `## KB context` with `kb_context_new`, only
   for the refs that moved or are new.
4. `architecture` trigger only: hand off to `sa-ticket-ground` (`--mission`
   for a mission). It refreshes `## Services & order` / `## Technical
   grounding` and the `Grounded on:` revision, then runs `kb ticket check`.
   For any other trigger, skip the SA and `kb ticket check`, which would
   otherwise force a re-ground after every dev commit. The BA skills still
   never read `-code` themselves.
5. Apply the B4 rules.
6. Bump `Revision` and append the change-log row.
7. Run `kb mission lint` / `kb ticket lint` until PASS.
8. Maturity review **of the changed sections only**: one round, the same
   rubric. Write the scores into the row's `Review` cell.
9. Amending a ticket: untick the DoR box(es) whose evidence changed. Only the
   BA re-ticks, which preserves the "agent never ticks DoR" rule. Update the
   `@ rev` pin (B4).
10. Hand the diff to the human. The agent never commits or pushes.

### B4. Change rules

- **Done stories are frozen.** A story `kb mission next` reports `done` keeps
  its backlog row unchanged. New or changed work becomes a new row with the
  next free number. Numbers are never reused or renumbered.
- **Not-yet-done stories** may be edited, and are listed in the change-log
  row's `Affected`.
- **Decisions are superseded, not edited.** A `DECIDED` row is never
  rewritten. Add `D<n>` with `Supersedes D<k>` in its Decision cell, and set
  D<k>'s status to `SUPERSEDED`. Two tool changes follow:
  - `kb ticket check`: a `[NEW: D<k>]` naming a `SUPERSEDED` row fails with a
    message naming the superseding row.
  - `kb mission next`: a `SUPERSEDED` row in `Blocks` is judged by the status
    of the row that supersedes it, following the chain, so stories never stay
    blocked for ever.
- **Tickets follow their mission.** The ticket line becomes
  `> Parent mission: <M-id> @ rev <N>`. `@ rev` is optional, and absent means
  rev 1. `kb mission next` reports a ticket `draft`, with reason
  `parent mission rev <M> affects this story`, when two things hold: the
  mission's revision is greater than the ticket's pin, **and** a change-log
  row after the pin lists the story in `Affected`. `kb ticket tidy` and every
  `Parent mission` parser must accept the optional suffix.

### B5. Publish interaction

Nothing extra. An amended item is re-published on the BA's next `kb publish`.
The hub's git history keeps every published version, and `Revision` plus
`## Change log` make the version readable inside the document.

## 6. Compatibility

- Old missions and tickets (no `Revision`, no `## Change log`, no `@ rev`)
  still PASS, with warnings only.
- An existing `ba` repo that re-runs `kb init --kind ba` gains the workflow,
  the skill, `.gitattributes` and the gitignore entry. Its `config.yaml` is
  untouched (it is protected), and until `intake:` is set, `kb publish` takes
  the snapshot route as today.
- `kb-doctor.yml` is unchanged. Its issue body gains `architecture` rows.

## 7. Decisions

Owner decisions:

1. Publish the plan to the hub now. Who may read it is decided later.
2. Follow the proposed direction ("theo đề xuất").
3. Publish path: on-demand `kb publish` (option B), with no hub change.

Designer's calls (open to override):

1. One document per `ba` repo (`<repo_id>-plan`), one group per mission.
2. Missions also need a fully ticked DoR to publish.
3. Citation staleness does not block publishing; the daily issue tracks it.
4. `## Review record` and `## Definition of Ready` are not published.
   `## Open questions` is.
5. The tracker flow is unchanged; the hub is a reference copy.
6. L2 carries every L3 table; `kb build` is not relaxed.
7. Drift baseline: the newest hub commit carrying the pinned `-code`
   revision. If there is none, report one `stale` finding with reason
   `baseline not on hub`.
8. Amendment reviews go in a `Review` column of `## Change log`.
9. The SA and `kb ticket check` run in amend only for an `architecture`
   trigger.
10. A disqualified item drops off the hub on the next publish; the
    `/kb-publish` diff shows it first.
11. Change log and revision apply to tickets as well as missions.
12. Existing repos add `intake:` by hand, per QUICKSTART.
