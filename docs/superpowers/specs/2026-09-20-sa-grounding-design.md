# SA grounding layer for the BA workflow — design

Date: 2026-09-20
Status: draft for review
Scope: `kind: ba` repos (templates shipped by `kb init --kind ba`), plus one
new CLI gate `kb ticket check`.

## 1. Problem

A BA works on a machine with no source checkout. The only technical
evidence available is the KB published on the hub — in particular each
product repo's `<repo>-code` document, generated by `kb code-ingest`
(deterministic, no LLM, no network).

What `<repo>-code` can prove, per section id:

| Section id | Proves | Does not prove |
|---|---|---|
| `svc.<name>` | container name, image, ports, `Depends on`, env **keys** | directory (no such field), responsibility, technology when built from source (`Technology \| none`) |
| `struct.tree` | tracked file paths to depth 4, at most 600 lines (a marker names the first dropped entry) | anything deeper or past the cap |
| `db.<table>` | columns from `CREATE TABLE` + `ALTER TABLE ADD COLUMN` | ORM-only tables, views, constraints beyond PK |
| `api.<tag>` | `METHOD /path` rows from a committed OpenAPI file, `servers[*].url` | request/response bodies, un-committed routes |
| `int.<name>` | an external system, inferred from env key names | how it is called |
| `cmd.build/test/lint/run` | the primary command verbatim + alternatives, each with its source | which test covers which AC |
| `dep.<eco>` | direct packages + detected frameworks | usage |

It never proves: call graphs, symbol maps, per-module flow, failure modes,
contract body schemas.

Today the `ba-ticket-author` skill both writes business content AND
reaches into `-code`/`-svc` for names, with `%%TODO: verify against
codebase%%` as the fallback. Nothing checks that a name it wrote exists.
The result is one writer for two kinds of facts and no machine gate on the
technical half.

## 2. Decisions (all confirmed 2026-09-20)

| # | Decision | Rejected alternative |
|---|---|---|
| A1 | New artifacts are package resources under `src/strata_kb/templates/init/`, wired into `initcmd.BA_TEMPLATES`, and reach a BA repo through `kb init --kind ba`. | Loose files under `docs/dev-flow/` and `.claude/agents/` in this repo — never shipped, dead docs. |
| A2 | The existing 15-section `ticket-template.md` stays as-is (it *is* the business half; `ticket.REQUIRED_HEADINGS` is a compatibility contract). One new SA-owned section `## Technical grounding` is added and listed in `ticket.RECOMMENDED_HEADINGS` (warning-level in `kb ticket lint`). | A 3-block `[BA]/[SA]/Gate` template: breaks `kb ticket lint` for every new ticket, forces a `REQUIRED_HEADINGS` change (major release). |
| A3 | The BA skills (`ba-ticket-author`, `ba-mission-plan`) stop grounding code detail. They write `%%TODO: verify against codebase%%` and hand the technical half to the SA skill. | Leave the BA skill as-is and add SA on top: two writers of code facts, one of them ungated. |
| A4 | `mission-template.md` gains one SA-owned section `## Services & order` (capability layer: `svc.<name>` + `Depends on` + reason). C4 sections unchanged. The same SA skill fills it (`--mission` mode). | A second, separate mission template; `kb mission lint` knows only one. |
| A5 | `kb ticket check` verifies `Grounded on: <doc-id> @ <revision>` against the `revision` field of the `-code` manifest it reads (hub mirror by default, local `--kb-dir` when the document exists there). Mismatch = "stale grounding", exit 1. `dirty_tree` is not persisted anywhere today; hub copies are produced by `kb-code.yml` from a clean CI checkout, so a revision match is the clean-tree proof. No change to `codeingest/core.py`. | Persist a dirty marker in `revision` (`abc1234-dirty`): touches the manifest contract read by `kb svc note` and every hub consumer. |
| A6 | SA skill name: `sa-ticket-ground` (verb form, like `ba-ticket-author`). | — |

Standing constraints from the brief: no new extractor; `mdutils.py` is
frozen; no call-graph generation (GitNexus covers that on the Dev side —
`Open decisions` is where those questions are parked); templates and skill
text in English; impact analysis before touching any symbol.

## 3. Ticket template — `## Technical grounding`

Inserted into `templates/init/ticket-template.md` directly before
`## Open questions` (so it sits with the other recommended sections and
before `## KB context`). Heading text is fixed English, like every other
heading. Verbatim:

```markdown
## Technical grounding
<!-- SA-owned — filled by /sa-ticket-ground from the hub's <repo>-code
document, never by the BA. Every line points at a section id that exists
in that document, or carries [NEW: <reason>], or is parked under Open
decisions. No internal flow, no failure modes — the document cannot
prove them. Gate: `kb ticket check <this file>` must report
`Grounding: PASS`. -->
- Grounded on: <repo-id>:<repo-id>-code @ <revision>
- Service: svc.<name>
- Files:
  - <path exactly as listed in struct.tree>
  - <path> [NEW: <why it does not exist yet>]
- Tables: db.<table>.<column>, … — or `none`
- Routes: api.<tag> — <METHOD> <path>, … — or `none`
- Externals: int.<name>, … — or `none`
- Verify with: cmd.test — `<primary command, verbatim>`
- Open decisions:
  - none
```

Field rules (the same rules `kb ticket check` enforces in §7):

- `Grounded on:` — one line, first in the section. `<repo-id>:` qualifier
  optional, same grammar as a `kb-context` ref (`kbcontext._REF_RE`).
  `<revision>` is the `revision` value from that document's
  `_manifest.yaml` (7-char commit as written by `core.run()`).
- `Service:` — one or more `svc.<name>` ids. No directory: the service
  record has no such field. A directory, when needed, is a `Files:` entry.
- `Files:` — one path per sub-bullet, spelled exactly as `struct.tree`
  lists it. A path the ticket will create carries `[NEW: <reason>]`.
- `Tables:` — `db.<table>.<column>`; the column must be a row of that
  table's L2 column table. A whole-table reference is `db.<table>`.
- `Routes:` — `api.<tag> — METHOD /path`; the pair must be a row of that
  tag's L2 table. Route without a pair is `api.<tag>` alone.
- `Externals:` — `int.<name>` ids.
- `Verify with:` — `cmd.test` (or `cmd.build`/`cmd.lint`/`cmd.run`) plus the
  command in backticks; the command must equal the section's `Primary:`
  or one of its alternatives table rows, byte for byte.
- `Open decisions:` — anything the document cannot prove: internal flow,
  failure modes, contract bodies, a business rule that contradicts the
  code facts, a table/route the BA assumed and the document lacks. `none`
  when empty. The gate fails while this list is non-empty.

There is deliberately no `Flow` field and no `Failure modes` field.

`## Definition of Ready` gains one checkbox line:
`- [ ] Technical grounding filled by SA; kb ticket check PASS (Open decisions empty)`.

Code change in PR 1: `ticket.RECOMMENDED_HEADINGS` gains
`"## Technical grounding"` (kept in template order, before
`"## Open questions"`). This is a warning in `kb ticket lint` when the
section is missing or empty — legacy tickets keep passing.

## 4. Mission template — `## Services & order`

Inserted into `templates/init/mission-template.md` after `## Sequencing`
and before `## Open questions`. Not added to
`mission.REQUIRED_MISSION_HEADINGS`. Verbatim:

```markdown
## Services & order
<!-- SA-owned — filled by /sa-ticket-ground --mission from the hub's
<repo>-code document. Capability layer only: one row per service this
mission touches, by its svc.<name> id; "Depends on" is copied from that
record's own `Depends on` cell. No file names, no function names,
no tables, no routes — those belong in each ticket's Technical grounding
section. A service the mission will create carries [NEW: <reason>]. -->
- Grounded on: <repo-id>:<repo-id>-code @ <revision>

| Order | Service | Depends on | Why this order |
|---|---|---|---|
| 1 | svc.<name> | <from record> | <reason, cites the dependency> |
```

Sources the SA may use for this section: the architecture document on the
hub, `svc.*` records (`Depends on`), `dep.*` (frameworks), `struct.tree`
(top-level layout). `db.*` and `api.*` are **not** loaded for a mission —
they pull the plan down to the wrong layer.

`kb mission check` is not in scope. The engine in §7 takes the heading as
a parameter so a later `kb mission check` is a small addition.

## 5. SA skill — `sa-ticket-ground`

Four package resources, same layout as every other BA skill, wired into
`BA_TEMPLATES`:

| Resource | Lands at |
|---|---|
| `claude-skill-sa-ticket-ground.md` | `.claude/skills/sa-ticket-ground/SKILL.md` |
| `claude-command-sa-ticket-ground.md` | `.claude/commands/sa-ticket-ground.md` (thin invoker: `Invoke the \`sa-ticket-ground\` skill with the Skill tool`) |
| `copilot-sa-ticket-ground.prompt.md` | `.github/prompts/sa-ticket-ground.prompt.md` (`mode: agent`) |
| `cursor-sa-ticket-ground.md` | `.cursor/commands/sa-ticket-ground.md` |

Copilot and cursor bodies identical except frontmatter line 2, like the
dev wrappers.

Frontmatter (skill):
`name: sa-ticket-ground` /
`description: Fill the SA-owned "Technical grounding" section of a BA ticket (or "Services & order" of a mission) from the hub's <repo>-code document — ids only, no inference. Use when a ticket has its business sections drafted and needs its technical half, or when the BA invokes /sa-ticket-ground.`

Inputs: a ticket file under `tickets/` whose business sections are drafted
(or a mission under `missions/` with `--mission`); the hub (MCP
`kb_search` / `kb_get_section`, CLI fallback `kb query` / `kb get`); the
architecture document on the hub. **No repository access** — the SA never
reads source code.

Workflow:

1. **Intake** — read the ticket. Identify the product repo (`<repo-id>`)
   from the BA's input or the mission. Collect every
   `%%TODO: verify against codebase%%` in the BA sections: these are the
   questions this pass must answer or park.
2. **Load** — from `<repo-id>-code` only: `struct.tree`, every `svc.*`,
   `cmd.test`, and the `db.*` / `api.*` / `int.*` sections whose names
   match the ticket's nouns. Read the manifest revision (`kb get` prints
   the citation `(<revision>)`; `kb_get_section` returns it) — this is the
   value for `Grounded on:`. With `--mission`, load `svc.*`, `dep.*`,
   `struct.tree` and the architecture document; do **not** load `db.*` or
   `api.*`.
3. **Fill** — write `## Technical grounding` (or `## Services & order`)
   from the loaded sections and nothing else. Each BA placeholder is
   either answered by an id here or parked under `Open decisions` with the
   placeholder's own words. The placeholder itself stays in the BA
   section untouched — the Dev reads the answer from this section.
4. **Gate** — run `kb ticket check <file>` (CLI). Fix every `[error]`
   and re-run until it prints `Grounding: PASS`. A non-empty
   `Open decisions` is a FAIL by design: report the list to the BA
   rather than emptying it by guessing.
5. **Handover** — report: ids grounded, `[NEW]` entries, open decisions
   (count + text), and any BA-section contradiction found. The BA decides
   what goes back to the business side and what goes to the Dev.

Hard rules (verbatim in all four wrappers):

```
- Every line in the SA-owned section (## Technical grounding, or
  ## Services & order with --mission) must either
    - point at a section id that exists in the <repo>-code document, OR
    - carry [NEW: <reason>] saying why it does not exist yet, OR
    - go under Open decisions.
- No data → Open decisions. Never infer; never fill from a generic
  pattern or from what "a service like this usually has".
- Never edit a BA-owned section. A business statement that contradicts
  the code facts goes under Open decisions, quoted, not corrected.
- The first line is `Grounded on: <repo-id>:<doc-id> @ <revision>`,
  copied from the document's own manifest revision. Ground only on the
  hub's copy — a document you cannot find on the hub is not a source.
- Never write internal flow; never write failure modes — the document
  cannot prove either. Those questions go to Open decisions for the Dev,
  who has the code and GitNexus.
- `kb ticket check` failing to RUN is not a PASS. No CLI → tell the BA
  to install strata-kb; never hand over an unchecked section.
- Never tick a Definition of Ready checkbox; only the BA confirms DoR.
- English headings stay English; write the section's free text in the
  BA's working language.
```

The SA is not a reviewer of the BA. It fills a different section; it does
not score.

## 6. BA skills — what changes

In all four wrappers of `ba-ticket-author` and all four of
`ba-mission-plan`:

- Remove the paragraph in the **Ground** step that presents `-code`/`-svc`
  hits and the `Technology | none` caveat.
- Remove the hard-rule bullet **"Ground code detail in the hub's code
  knowledge before reaching for a placeholder"** with its two sub-bullets
  and the `Container(alias, label, technology, description)` guidance.
- Add one hard-rule bullet in their place:
  `Code-level detail is not yours to ground. Write %%TODO: verify against codebase%% where a service, table, route or file name is needed, add the owned Open questions row, and hand the ticket to /sa-ticket-ground once the business sections are drafted. Never read <repo>-code or <repo>-svc yourself.`
- In the **Ground** step, add: a hit tagged `code`

## 7. `kb ticket check` — the machine gate (PR 2)

### 7.1 CLI

```
kb ticket check <ticket.md | -> [--kb-dir .kb] [--hub URL] [--json]
```

Registered on the existing `ticket_app` next to `lint`. Reads the file
(or stdin) the same way `ticket_lint` does (UTF-8 errors → red line,
exit 1). Resolves the hub through the existing `_hub_or_exit(hub, kb_dir)`
only when the document is not found locally (§7.3).

Exit codes: `0` — every check passed and `Open decisions` is empty;
`1` — any `[error]`. No exit 2 (there is no staleness tier here: a
revision mismatch is an error).

Output mirrors `LintReport.render()`: one `[error]`/`[warn]`/`[note]`
line per item, every error line ends with `(line N)` naming the ticket
line, last line `Grounding: PASS` or `Grounding: FAIL`. `--json` emits
`LintReport.to_json()`.

### 7.2 Engine — `src/strata_kb/ticketcheck.py`

No CLI/MCP imports (same split as `ticketlint.py`). Public entry:

```python
def check(text: str, *, heading: str = "## Technical grounding",
          load_doc: Callable[[str | None, str], LoadedDoc | None]) -> LintReport
```

`LoadedDoc` = manifest (`models.Manifest`) + a reader for one L2 group
file (`file -> str | None`). The caller (CLI) decides where documents come
from (§7.3); the engine only parses and compares. `heading` exists so a
later `kb mission check` reuses everything.

Parsing, in order:

1. `lintcore.section_body(text, heading)` — `None` → error
   `missing '## Technical grounding' — run /sa-ticket-ground`; stop.
   Body is read through `lintcore.visible_body` (HTML comments stripped).
   Line numbers: index of the heading line in `text.splitlines()` plus
   the offset inside the body.
2. `Grounded on:` — regex
   `^-\s*Grounded on:\s*(?:(?P<repo>[A-Za-z0-9][A-Za-z0-9._/-]*):)?(?P<doc>[A-Za-z0-9][A-Za-z0-9._-]*)\s*@\s*(?P<rev>[0-9a-fA-F]{7,40})\s*$`
   (repo/doc classes as in `kbcontext._REF_RE`). Missing or malformed →
   error; stop (nothing else can be checked without a document).
3. `load_doc(repo, doc)` → `None` → error naming what was looked for and
   where (`<kb_dir>/<doc>` and `federation/<repo or *>/<doc>`); stop.
   Manifest unreadable → the loader raises a typed error; the engine
   reports `could not read <path> (<exc>)` as an error and stops. Never a
   traceback.
4. Revision: `manifest.revision` and `rev` must agree by prefix in either
   direction (7-char vs 40-char). Mismatch → error
   `stale grounding: ticket says @<rev>, <doc> on the hub is @<manifest.revision> — re-run /sa-ticket-ground`.
   Empty `manifest.revision` (document generated outside git) → warning,
   check continues.
5. Known ids = `{s.id for s in manifest.sections}`.
6. Id scan over every visible body line: regex
   `\b(svc|db|api|int|cmd|dep|struct)\.[A-Za-z0-9_][A-Za-z0-9_.-]*`.
   For `db.` matches, split off a trailing `.column` only when the
   two-part id `db.<table>` is known and the three-part id is not. A line
   containing `[NEW` exempts the ids on that line and emits
   `[note] new: <id> — <reason>` (reason = text after `NEW:` up to `]`;
   empty reason → warning `[NEW] without a reason`). Any other unknown id →
   error `unknown id '<id>' — not in <doc> (line N)`.
7. Column check: for each `db.<table>.<column>`, slice `db.<table>` from
   the group file named by that section's manifest `file` via
   `mdutils.slice_section`, take `lintcore.table_rows`, header column
   `Column`; missing column → error. Group file unreadable → warning
   naming the file, column checks for that table skipped.
8. Route check: on every line holding an `api.<tag>` id, each
   `\b(GET|POST|PUT|PATCH|DELETE|HEAD|OPTIONS)\s+(/\S*)` pair must be a
   `(Method, Path)` row of that tag's L2 table; otherwise error. Same
   unreadable-file degradation as 7.
9. Command check: on every line holding a `cmd.<x>` id, the first
   backticked span must equal the section's `**Primary:**` backtick
   value or a `Command` cell of its alternatives table; otherwise error
   `command not in cmd.<x> — copy the primary or an alternative verbatim`.
   A `cmd.` line with no backticked span → warning.
10. Files: the sub-bullets between the `- Files:` line and the next
    top-level `- <Field>:` line. Each entry's path (text before ` [NEW`)
    is looked up in the set of paths reconstructed from `struct.tree`'s
    L3 fence (`structure.raw.md`): a line ending in `/` is a directory
    with its full relative path; a file line is `<indent>- <name>` whose
    directory is the nearest preceding directory line with a smaller
    indent (root files have no directory). Outcomes:
    - found → ok;
    - `[NEW: …]` → note;
    - not found and the path has more than 4 segments, or the fence
      carries the `# … N more entries omitted` marker (the marker names a
      bare file name, so order is not comparable — every absent path on a
      capped tree is unverifiable) → warning
      `cannot verify '<path>': beyond struct.tree depth/line cap` (the
      SA is told to list the deepest verifiable directory instead);
    - otherwise → error `file '<path>' not in struct.tree (line N)`.
    `structure.raw.md` unreadable → warning naming the file, all file
    checks skipped.
11. Open decisions: sub-bullets under `- Open decisions:`. Items other
    than `none` / `N/A` (case-insensitive, trimmed) → one error each
    `open decision: <text> (line N)`, plus a summary line
    `N open decision(s) — resolve before Dev`.
12. Sanity: no `Service:` line with a `svc.` id → warning.

### 7.3 Where the `-code` document comes from

The CLI builds `load_doc` as: local first, hub second.

- Local: `<kb_dir>/<doc>/_manifest.yaml` exists → read it and its group
  files from there. Emit `[note] <doc> read from <kb_dir>` (Dev machines,
  and the hub's own checkout, hit this branch).
- Hub: `_hub_or_exit(hub, kb_dir)` → `federation.load_federation(handle.federation_dir)`.
  With a repo qualifier: the entry whose `meta.repo_id == repo`. Without:
  the entries holding `<kb_dir>/<doc>/_manifest.yaml`; exactly one → use
  it; zero → not found; several → error listing the holders and asking
  for the `<repo-id>:` qualifier (same rule as `resolve.resolve_refs`).
  Emit `[note] <doc> read from hub federation/<repo-id>`.

A BA repo has no local `-code`, so it always takes the hub branch — which
is the point: the SA grounded on the hub, the gate verifies against the
hub.

### 7.4 Tests

- `tests/test_ticketcheck.py` — engine, hermetic. Fixture: run
  `codeingest.core.run()` over `tests/fixtures_coderepo.build_code_repo`
  (git-initialised in `tmp_path`, as `test_codeingest_*` already do) to
  get a real `demo-code`; a `load_doc` that reads from that directory.
  Cases, each a small ticket body built from the §3 block:
  - golden section → PASS, no errors;
  - unknown `svc.`, `db.`, `api.`, `int.` ids → one error each, with the
    right line number;
  - `db.restrictive_airspace.nope` → column error; `.designation` → ok;
  - `api.airspace — DELETE /airspace` → route error; `GET /airspace` → ok;
  - `cmd.test — \`pytest -q\`` → command error; primary and `pytest`
    (alternative) → ok;
  - `Files:` present path ok, missing path error, `[NEW: …]` note,
    5-segment path warning, path after the truncation marker warning
    (fixture with >600 tree lines built in-test);
  - `Open decisions` with one item → error + summary, exit contract via
    `LintReport.passed`;
  - revision mismatch → stale error; empty manifest revision → warning;
  - missing section, missing `Grounded on`, unreadable manifest,
    unreadable `db.md` → the documented error/warning, never an exception;
  - `[NEW` with empty reason → warning.
- `tests/test_cli_ticket_check.py` — `CliRunner` over `app`: exit 0 on the
  golden ticket, exit 1 on a bad id with the id named in output, `--json`
  shape, stdin (`-`), local `--kb-dir` branch, hub branch through the
  `fed_hub` fixture with a published `demo-code`, ambiguous holders error.
- `tests/test_templates.py` / `tests/test_init.py` — PR 1: the four
  `sa-ticket-ground` resources exist and are wired for `ba` only (not
  `hub`/`child`/`dev`); the hard-rules block is byte-identical across the
  four; copilot/cursor differ only on frontmatter line 2; the two
  templates carry the new sections; `RECOMMENDED_HEADINGS` carries the new
  heading; BA wrappers no longer contain `Container(alias, label,` and do
  contain `/sa-ticket-ground`.
- `tests/test_ticketlint.py` — a ticket without `## Technical grounding`
  still passes (warning only); the template's own block is not flagged
  as empty.

### 7.5 What the gate does not do

- It does not read source code. Only `-code` documents.
- It does not validate business sections — that is `kb ticket lint`.
- It does not check `-svc`. `svc.<id>` is validated against `-code`, the
  same join key `kb svc note` uses.
- It does not run in `kb-ticket-lint.yml` yet (follow-up, §9).

## 8. Rollout

**PR 1 — templates and skills (markdown + two constant edits).**
Files: `ticket-template.md`, `mission-template.md`, four
`*-sa-ticket-ground*` resources, eight BA wrapper edits, `QUICKSTART-ba.md`,
`initcmd.BA_TEMPLATES` (+4 rows), `ticket.RECOMMENDED_HEADINGS` (+1),
tests in §7.4 last two bullets, and one README paragraph in the BA
workflow section (BA drafts → SA grounds → `kb ticket check`).
Impact analysis before editing `BA_TEMPLATES` and `RECOMMENDED_HEADINGS`
(both are imported by tests and `ticketlint`). **No version bump — ever, in
either PR.** `pyproject.toml`'s `version` and `uv.lock` stay untouched; the
CHANGELOG entry goes under an `## Unreleased` heading. Releasing and
bumping is the maintainer's separate act (decided 2026-09-20).

**PR 2 — `kb ticket check`.** Files: `ticketcheck.py` (new), `cli.py`
(one command on `ticket_app`), two test files, README command table +
exit-code row (the `test_readme.py` exit-code pin lists producers of exit
2 — this command adds none, so that assertion is unchanged). No new
dependency; no version bump; `uv.lock` untouched. `detect_changes` before
commit per CLAUDE.md. Shipped 2026-09-20 as planned in
docs/superpowers/plans/2026-09-20-sa-grounding-pr2-ticket-check.md.

**After PR 2 — measurement, not code.** Smoke the gate first on this
repository itself: local hub (`kb init --kind hub`, no remote → direct
publish), `kb code-ingest` + `kb publish` from strata-kb, a `kind: ba`
repo pointed at that hub, one ticket through BA → SA → `kb ticket check`.
strata-kb has no compose file, so `svc.*` is empty there — this smoke
proves the pipeline, not the document. Then run `/sa-ticket-ground` on
three real vertical-slice tickets of the product repo and count
`Open decisions` items per ticket, split into "code does not exist yet"
(`[NEW]`) and "code exists but the document cannot see it".
Consistently empty → the document is sufficient. Consistently ~5 →
find which extractor lacks a field and extend *that extractor*; do not
add an agent.

## 9. Out of scope / follow-ups

- Auto-invoking SA after BA (hook or pipeline) — manual until the flow is
  stable.
- A third-tier reviewer agent, or a scoring rubric for the SA section.
- `kb mission check` (engine already parameterised by heading).
- `kb_ticket_check` MCP tool (the CLI has no fallback today, like
  `kb mission lint`; the SA wrappers say so).
- Adding `kb ticket check` as a step in `kb-ticket-lint.yml`.
- A separate mission-plan agent — SA is shared; split only if the two
  layers actually conflict in practice.
